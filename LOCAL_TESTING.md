# Test the Franko redesign locally

This source archive is a complete Expo project; extract the `Franko-App` folder before running it. It does **not** contain `node_modules`, build artifacts or the private `credentials.json` file.

```sh
cd Franko-App
npm ci
npm test
npm run web
```

For a native preview, run `npx expo start --go` and scan the QR code with a compatible Expo Go app, or use your existing development build with `npm start`. The existing API endpoints, cart, checkout and navigation routes remain wired to the original backend. Testing live products/checkout requires that backend to be reachable from your device.

## What to check

1. **Home on a small phone and a tablet:** carousel remains first, the search field is long and the logo sits near the left edge. The bundled Franko campaign appears immediately while offline/loading; remote ads only enter the slider *after* they are cached. No mint rectangle should slide across before an ad. Home cards, header and bottom tab all use a shopping-cart icon. The campaign uses the approved `#84e8b9` background; product actions and prices consistently use Franko `#086942` (red remains reserved for sales/errors). Rotate the device and confirm the banner and category tiles fit.
2. **Product cards and listings:** home shelves, Phones, Laptops, Fans, other categories, All Products, Brands, Showroom, Search, Wishlist and Recently Viewed now use the *same* 280-point-high product card, image, two-line name, price block and cart button. The button has a **separate row below the price**; check a product with a long price/old price on a narrow phone. All app text and inputs use bundled Inter; the local ZIP includes the package lock so `npm ci` installs its fonts. Cards use two columns on phones, three on mid-size tablets and four on larger screens; filter sheets fit the visible height. On a fresh listing visit start at the top; scroll, open a product, and go back to verify position restoration.
3. **Lazy loading:** the category, brand and showroom APIs return complete datasets; their cards now **mount progressively in 12-item batches** as the list approaches the end (this is *client-side rendering*, not backend pagination). All Products continues to fetch real 24-item pages from the existing paginated API, stopping when the final page is reached. Home shelves remain virtualized. Verify scrolling, sorting, filtering and add-to-cart on both the first and later batches.
4. **Product details:** check the responsive image, zoom modal, price, availability, specs and sticky quantity/cart controls in portrait and landscape. Test recommendations, cart updates, wishlist and return navigation. Search results and Recently Viewed should keep their position when returning from a product.
5. **Scrolling and speed:** “Need help?” should hide while scrolling and come back roughly one second after stopping. Home shelves and lists mount small batches; the remote image cache prefetch queue is bounded. Browser/native may still emit performance warnings if the device, network, or a third-party component is slow; the app does not intentionally suppress them.
6. **Orders/account:** checkout still shows Delivery, Payment and Review, individually carded items, original validation and payment flows. Account retains Orders, Wishlist, Addresses and Help; the address screen offers Add when empty. Test payment with your own safe staging workflow only.

## Database loading, product images and campaign (new)

1. On a clean install with a connection, open Home and a category listing. A visible, small **“Loading products from Franko…”** notice and skeleton cards should appear while the real product endpoint responds. Reopen with saved products: cards paint immediately, with **“Checking latest products…”** and a spinner until the database-backed API request completes. Search, Brand, Showroom and All Products have the same non-blocking indicator. If the connection fails, previously cached products stay visible.
2. Check products whose API supplies `productImage`, `imagePath`, `ProductImage` or a complete image URL. The image must come from that product record (not a bundled product picture); a delayed spinner shows only if its image takes more than a moment. Expo Image stores successfully downloaded remote pictures in memory and on disk, and the prefetch queue warms nearby cards without competing with the carousel.
3. Visit the same listing a few times and restart the app on a device: product records should refresh, but previously viewed image URLs should reuse the disk copy, not be downloaded again. Test again more than five minutes later—the image URL must **not** acquire a new timestamp. Change the test product's image path/revision on the backend and confirm only that changed image downloads anew.
4. Before remote ads have loaded, the bundled first carousel frame must show the **Franko logo over the mint campaign image**. Once downloaded, remote ad images replace that frame without a blank green slide.

## Catalog freshness and web/search regression

1. With a connection, open Home, Phones, Computers, Brands and All Products. Reopen the app with previously saved listings: products/images should appear immediately from cache, then update quietly from the real API. Add a product in your **test backend** and verify it appears on the relevant screen after returning to that screen or within about two minutes while browsing; home pull-to-refresh immediately rechecks the main shelves and full catalog. Old/deleted entries should disappear after a successful refresh, but stay visible temporarily if offline. All Products still uses the backend's original 24-item pagination; how quickly an item appears on *page one* also depends on the backend's page ordering.
2. Product and ad image URLs now stay **stable across catalog refreshes, revisits and time passing**. On native devices, Expo Image uses the memory/disk cache and the background prefetch queue checks disk before any new fetch; a successfully rendered image is not prefetched again in the same session. A renamed picture, or an API-provided `imageVersion`, `imageModifiedDate`, `dateModified`, etc. change, gets a **new cache key** and downloads once. If the backend overwrites the exact same file URL without changing any revision field, the app cannot know its bytes changed without requesting it again: update the image path/revision in the API to make the replacement visible. On web, the browser's HTTP cache governs persistence across reloads, so the image server must allow caching for a strict no-repeat-download guarantee. The OS/browser can evict cached files. Prefetch remains bounded; no blank green slider should precede remote ads.
3. On a clean installation/cleared storage, start the app without signing in. Home should open **without an automatic sign-in/signup modal**. Open Search by tapping the search bar and type a product name: no `useWindowDimensions` ReferenceError. Protected account/checkout actions and a genuinely expired signed-in session may still request sign-in.
4. Test `npm run web` or an embedded web view. The invoice PDF library should no longer throw `tslib.default`/`__extends`; try downloading an invoice for a test order. Local RN shadow styles are converted to `boxShadow` on web only, while native shadows are retained. Third-party library warnings may still be outside this conversion.

## Session-expiry regression

1. Sign in with a test customer and open Orders. In a **test environment**, invalidate the saved refresh token on the server, then trigger an Orders refresh. When both the order request and refresh return 401, customer details and order/address/checkout drafts should disappear from AsyncStorage and Redux, and the visible sign-in modal should open once. The cart is deliberately retained. No repeating “Backend request failed” banner should remain on Orders.
2. Verify that an expired **access** token with a *valid* refresh token renews silently while the app is active, and Orders loads normally. A temporary network outage or refresh-server 5xx must not wipe the saved account.
3. Leave the app in the background until the access token expires, then resume; it should sign out on return. Also check cold start with an already expired refresh token. Mobile platforms may suspend background JavaScript, so sign-out while fully backgrounded is enforced on resume/startup (rather than claiming an OS-guaranteed background timer).
4. Check that the sign-in form is **visible** after redirect and that a fresh login works. Test on a device with backend access; the offline tests do not exercise a live customer session.

`npm test` checks all 39 registered screens, relative imports, static UI contracts, mocked catalog freshness/image/search regressions, and mocked auth-session regression cases (401/refresh, storage/Redux cleanup, transient errors, startup/resume and stale responses). The source was also bundled with Expo for web, Android and iOS; these checks do **not** prove a device-specific layout or complete a live checkout. Product/ad data and payment testing need the existing Franko backend reachable from your device. The JS stack that used the deprecated `InteractionManager` has been replaced with the native stack, and app `SafeAreaView` imports use `react-native-safe-area-context`.

This package is for local testing. No commit, push or pull request is needed to try it.
